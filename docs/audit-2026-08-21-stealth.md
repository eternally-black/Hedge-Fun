## 1. Реальные деньги — чинить до запуска

### 1.1 [V] CRIT — повторный вывод средств
`src/app/api/real/withdraw/route.ts:130`

Ветка SUBMITTING: если `tryConverge` говорит, что прошлый ран **завершился**, код ставит `existing.state = "DONE"` и **проваливается дальше**. Ниже `reusable` требует `existing?.state === "FAILED"`, поэтому переиспользования нет — минтится новый bridge-forwarder и стартует второй `startWorkflow`.

Сценарий: пользователь выводит часть баланса, браузер умирает на поллинге, UI показывает ошибку, пользователь жмёт «вывести» снова → перевод уходит второй раз. Спасает только полный дренаж кошелька (тогда `insufficient_balance`); частичный вывод платится дважды.

Фикс: при `converged === true` вернуть исход прошлого рана (200 + его txHash), а не проваливаться в минт. Проваливаться только когда прошлый ран действительно FAILED.

### 1.2 [V] HIGH — POSTED с `externalOrderId = null` невидим для всех свипов
`src/app/api/real/submit/route.ts:273-276`

`orderId` берётся из ответа биржи опортунистически; если поля нет — строка уходит в POSTED с NULL. Комментарии в самом файле (`:149`, `:187`, `:234`) подтверждают: все reconcile-сканы фильтруют по non-null `externalOrderId`. Деньги потрачены, позиции в БД нет, слот рынка занят навсегда, а `/api/real/posted` отобьёт легитимный отчёт 409-м.

Фикс: не переводить в POSTED без id — оставлять SUBMITTING и запускать discovery/read-back.

### 1.3 [V] HIGH — builder-креды раздаются каждому браузеру
`src/app/api/builder/sign/route.ts:210-211`

Ответ содержит `POLY_BUILDER_API_KEY` и `POLY_BUILDER_PASSPHRASE`. Это осознанное решение (комментарий на `:7`), но это общий на всё приложение долгоживущий секрет, который получает любой пользователь, прошедший consent. Один злонамеренный клиент держит его вечно, независимо от протухания токена.

Фикс на будущее: проксировать builder-запросы через сервер; минимум — ротация по расписанию и признание утечки штатным сценарием.

### 1.4 [U] HIGH — победа списывается без доказательства (neg-risk)
`src/lib/real-settle.ts:150`

Проверка выигрыша читает ERC-1155 баланс на CONDITIONAL_TOKENS, но для neg-risk позиций токен обёрнут на NegRiskAdapter — баланс всегда 0. Выигрыш засчитывается в момент, когда Gamma напишет исход, без движения коллатерала.

### 1.5 [U] HIGH — проигрыш списывается по слову Gamma
`src/lib/real-settle.ts:88`

`conditionResolution()` из `polygon.ts` существует, но не вызывается. Ошибочный или преждевременный исход у Gamma → позиция закрывается как LOSS в $0, свип на неё больше не смотрит, а on-chain токены всё ещё платят.

### 1.6 [U] HIGH — комиссия может списаться дважды
`src/lib/orders.ts:171`

BUY-ордер валидируется против `allInCapMicro` (потолок с заложенной комиссией), а не против котированной суммы. Клиент подписывает makerAmount = потолок, биржа исполняет, платформенная комиссия начисляется сверху → списание = стейк + 2×комиссия.

### 1.7 [U] HIGH — оркестратор ордеров теряет заполнения
- `src/lib/order-probe.ts:96` — `hasMore: true` без курсора считается полным чтением: сделка на второй странице не находится, атака помечается KILL, деньги потрачены.
- `src/lib/reconcile.ts:113` — сравнение размеров строгим равенством, плюс свип перестаёт брать строки старше 48 часов → зависшая POSTED-атака навсегда.
- `src/lib/quote.ts:352` — клип `marketableBuyBoundBp` съедает запас в один тик при цене ≥ 99%: FAK-ордер отбивается («no orders found to match»).

### 1.8 [U] HIGH — воркфлоу может повторить завершённый денежный шаг
- `workflow.ts:280` — ветка DONE перезапускает ран, когда `verify()` вернул false; «unknown» (проба недоступна) читается как «эффекта нет» → повторный BRIDGE_OUT теми же входными данными.
- `workflow.ts:118` — фенс принимает и `PENDING_SIGNATURE`, и `SUBMITTING`, поэтому два параллельных ответа могут крутить один и тот же генератор.
- `scripts/resolve-workflow.ts:49` — оператор может пометить ран `failed` при непустом `txHash`; слот освобождается, адрес переиспользуется, вывод уходит дважды.

### 1.9 [U] HIGH — клиент говорит «не вышло», когда деньги уже ушли
`src/app/screens/RealOrderCard.tsx:127`

Нет ветки «отправлено, исход неизвестен»: если браузер запостил ордер на Polymarket, а отчёт серверу не дошёл, карточка показывает обычную ошибку. Естественное следующее действие — нажать «Buy» ещё раз.

Рядом: `RealWithdrawCard.tsx:165` — двойной тап проходит сквозь подтверждение вывода (первый клик выставляет `confirming`, второй уже отправляет, панель «проверьте адрес» не успевает отрисоваться).

## 2. Бумажная экономика — фармится

### 2.1 [V] HIGH — гонка на трате артефакта
`src/lib/streak.ts:205-217`

`recoverStreak` внутри `prisma.$transaction` с дефолтной изоляцией (Read Committed): читает `bal.artifacts < 1`, затем `decrement: 1`. Параллельные запросы проходят гейт все. `topup.ts` для той же операции использует `runSerializable` — здесь забыли.

Фикс: `runSerializable`, либо атомарный `updateMany({ where: { userId, artifacts: { gte: 1 } }, ... })` с проверкой `count`.

### 2.2 [V] HIGH — бесконечный поток шардов из ленты
`src/lib/shards.ts:26-27, 53-72` + `src/lib/swipe.ts` + `config.ts:95-106`

FEED-ставки не считаются в `SWIPE_CAP` и идут с `bypassCap` — не читают и не увеличивают `shardCount`. 20 шардов = артефакт, артефакт = `TOPUP_GRANT_CENTS` = $200 бумажных. Смягчает только гейт «Cash < $50» в `topup.ts`, то есть это не печатный станок, а бесконечный респавн: проиграть всё нельзя в принципе.

Плюс сам дневной кап неатомарен: `counter.shardCount` читается на `:59`, инкремент отдельным запросом на `:70`.

### 2.3 [U] HIGH — рефералка открывается мультиаккаунтом
`src/lib/referral.ts:38` — при отсутствии `REFERRAL_HASH_SECRET` или null-хэшей device-гард просто пропускается; квалификация считает нескапленные FEED-ставки, то есть проходится за минуты.

### 2.4 [U] HIGH — окно x2 очков отвязано от реальной серии
`src/lib/points.ts:96` — окно якорится к последнему дню со свайпом на `currentLevel` календарных дней; серию можно держать одними GM-тапами, а свайпы копить и получать x2 практически на всю историю.

## 5b. Отклонено как ложные срабатывания (проверено по коду)

- **`orders.ts:171`, BUY против `allInCapMicro`** — уже закрыто на вызывающей стороне: `submit/route.ts:114` передаёт `params.amountMicro`, с комментарием ровно про этот риск. Модель не видела submit-роут (он был у неё в blind spots).
- **`workflow.ts:118`, гонка двух драйверов на одном генераторе** — между `live.get` и `live.delete` нет `await`; JS однопоточный, второй запрос всегда получает `undefined`. Single consumer держится.
- **`sameOrigin` fail-open при пустом `APP_ORIGIN`** — `instrumentation.ts` жёстко требует `APP_ORIGIN` в проде и падает на старте.
- **Шардовые гонки «через settle.ts»** — `settle.ts` уже Serializable. Реальная дыра была в `orders.ts` и `real-settle.ts` (дефолтная изоляция) — она и закрыта.
- **Двойная ставка двойным тапом в мобилке** — блокируется unique-индексом `[userId, marketId, mode]`.
- **Всё про «пользователя убрали из allowlist»** — `isRealMoneyEligible` возвращает `true` безусловно, allowlist удалён осознанно. Правка №14 поэтому защитная, а не закрытие живого бага.

## 5c. Осталось открытым — нужно твоё решение или проверка вне кода

1. **Neg-risk winner proof (`real-settle.ts:150`)** — победа списывается по нулевому балансу на `CONDITIONAL_TOKENS`. Правда ли, что neg-risk позиция там всегда 0 (токен обёрнут на NegRiskAdapter), я по репозиторию не проверю. Подозрительно, что `market.negRisk` в этом запросе выбирается и нигде не используется. **Нужна проверка на цепочке** до любой правки: «починить» вслепую можно в обе стороны.
2. **FEED-шарды без капа → артефакт → $200 top-up** — задокументированное продуктовое решение (`config.ts:96`, `shards.ts:26`). Экономика, не баг: менять — твой вызов.
3. **Builder key + passphrase уезжают в браузер** — осознанный дизайн (`builder/sign/route.ts:7`). Закрыть можно только проксированием через сервер.
4. **Бэкапы без пароля шифрования** — «unset → plaintext + nightly WARN» тоже задокументировано. Жёсткий отказ означал бы отсутствие бэкапов на свежем хосте.
5. **Убыток списывается по Gamma без сверки с цепочкой** — у автора есть явная модель: цепочка опережает Gamma и опрашивается при задержке (`poller.ts:104-114`). Сверка на каждом убытке — это RPC на каждую ставку.
6. **`@@unique([userId, marketId, mode])` блокирует хедж на уже сыгранном рынке** — обрабатывается чисто (409 `already bet this market`), но требует миграции и продуктового решения.
7. **`settle.ts:160`, один throw вешает сеттл всего рынка** — catch не спасёт: транзакция в Postgres после ошибки уже aborted. Нужны SAVEPOINT или разбиение на чанки.
8. **Ops-бэклог**: advisory-lock на поллер, пиннинг GitHub Actions по SHA, HSTS, перевод CSP из Report-Only, WAL/PITR вместо ночного дампа.
